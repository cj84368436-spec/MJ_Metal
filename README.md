# 우리 썸인가 (secret-five)

이미 아는 두 사람이 다섯 장의 대화 카드에 각각 답하는 앱인토스 미니앱입니다. 두 답이 모두 YES일 때만 질문과 결과 문장을 공개합니다.

## 바로 실행하기

Node.js 24에서 확인했습니다. 브라우저 Mock은 계정이나 환경변수 없이 실행됩니다.

```sh
npm ci
npm test
npm run dev
```

브라우저에서 http://localhost:5173 을 엽니다. 모바일 크기로 화면을 줄이면 세로 레이아웃을 확인할 수 있습니다.

1. **5장 고르기 시작**에서 랜덤 또는 직접 고르기를 선택합니다. 직접 고르기는 같은 팩에서 정확히 다섯 장을 골라야 시작합니다.
2. 앞 세 장은 첫 번째 버튼, 나머지는 두 번째나 세 번째 버튼으로 답한 뒤 **카드 봉인하고 보내기**를 누릅니다. 새로 고쳐도 작성 중인 답과 방이 유지됩니다.
3. 방 아래 **모의 테스트 · 보낸 사람 → 받는 사람으로 보기**를 누릅니다. 두 화면을 함께 보려면 복사한 링크를 같은 브라우저 프로필의 새 탭에 엽니다. **나도 답할래**에서 다섯 장 모두 첫 번째 버튼으로 답한 뒤 **답 보내기**를 누릅니다.
4. 두 좌석 모두 **5장 중 3장이 통했어요**와 겹친 비율 60%, 심리 분석 카드(**호감 확률 74%**)를 봅니다. 둘 다 YES인 카드는 **두 장까지 무료**로 열리고, 나머지 한 장은 **나머지 1장 열기 · 1,100원** 또는 **1,900원 전 팩 패스** 뒤에 있습니다. 그 아래 **광고 보고 1장 무료로 더 열기**를 누르면 모의 광고가 끝난 뒤 한 장이 더 열립니다. 상대의 원본 응답이나 서로 다른 카드의 내용은 결과에 포함하지 않습니다.
5. 홈에서 **내가 그렇게 좋아?**를 선택해도 보내기는 무료입니다. 결과 화면에서 결제 시트를 닫으면 방은 그대로 남고, **1,100원으로 열기**를 누르면 이 방의 통한 카드 전부와 카드별 한마디가 열립니다(모의 결제). **1,900원 전 팩 패스**를 고르면 이 기기에서 만드는 4개 팩 방이 모두 열립니다. 두 좌석 모두 같은 열린 결과를 봅니다.
6. **우리 썸인가**(무료 팩)도 통한 카드 두 장까지 무료이고, 세 장 이상이면 나머지는 1,100원이나 전 팩 패스로 엽니다. `/demo`는 세 장 일치 예시이고 공유 링크·방·결제를 만들지 않습니다.

기본 Mock은 같은 출처의 localStorage에 두 좌석을 시뮬레이션합니다. 시크릿 창, 다른 브라우저 프로필, 다른 기기에서 링크를 사용하는 경우 아래 공유 방 설정이 필요합니다. Mock 저장소에는 양쪽 답이 들어 있으므로 실제 두 사람의 비밀 응답은 서버 모드를 사용합니다.

## 빌드와 검증

```sh
npm run build
npm run preview
```

`build`는 TypeScript 검사와 Vite CSR 빌드를 실행한 뒤 SDK 3.10.0의 `ait build`로 프로젝트 루트에 `secret-five.ait`를 만듭니다. `dist/`를 웹에 올릴 때는 `/r/*`, `/demo`, `/library` 같은 진입 경로를 `index.html`로 연결합니다.

`npm test`는 60문항 구조, 팩 내 5장 선택, 최근 3판 회피, 9가지 답 조합, 잠금 해제 전 두 장/후 전부 공개, 광고로 한 장 더 열기, 무료 팩의 두 장 무료·나머지 결제, 통한 카드 수별 호감 확률과 다음 행동, 방 만료, 재제출, 사용자 문구를 검사합니다. 공유 방 테스트는 PGlite의 PostgreSQL에서 실제 마이그레이션(001~005)을 실행하고 익명 API 역할로 접근 권한과 응답 범위를 검사합니다. 서버의 무료 미리보기·광고 카드 수는 `src/domain.ts`의 `previewCards`·`adBonusCards`와 같은지, `state` 응답에 상대의 원본 응답이나 어긋난 카드 id가 섞이지 않는지도 함께 확인합니다.

## 두 기기의 공유 방

1. Supabase 프로젝트의 SQL Editor에서 [방 마이그레이션](supabase/migrations/001_rooms.sql), [결과 잠금 해제 마이그레이션](supabase/migrations/002_result_unlock.sql), [팩 이용권과 집계 마이그레이션](supabase/migrations/003_pack_pass_metrics.sql), [보상형 광고 마이그레이션](supabase/migrations/004_rewarded_ad.sql), [5.0 결제 규칙 마이그레이션](supabase/migrations/005_preview_two_and_pass.sql)을 순서대로 한 번씩 실행합니다. 이미 004까지 적용한 DB에는 005만 추가하면 됩니다(005는 001~004를 지우지 않고 함수만 다시 정의합니다). 응답 테이블은 비공개 스키마에 두고, 클라이언트는 좌석 토큰을 검사하는 RPC만 호출합니다.
2. 프로젝트 루트에 `.env.local`을 만들고 다음 값을 설정한 뒤 개발 서버를 재시작하거나 다시 빌드합니다. 공개 키를 사용합니다.

```dotenv
VITE_DATA_MODE=shared
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

3. 같은 배포 주소를 두 기기에서 열어 테스트합니다. 방장은 방장 토큰을 로컬에 보관하고, 초대 링크에는 게스트 토큰 하나만 실립니다. 게스트의 첫 제출을 봉인하며, 방의 유효 기간은 7일입니다. 대기 중인 방장은 화면이 보일 때 3초마다 상태를 확인합니다. 네트워크 제출 실패 시 같은 탭에 답을 보관하고 재시도합니다.
4. 공유 방의 모의 잠금 해제를 시험할 **테스트 DB**에서만 다음 설정을 켭니다. 기본값은 꺼짐입니다. 방 만들기는 무료이고, 결과를 열 때만 이 설정이 필요합니다.

```sql
update secret_five_private.settings set test_purchases = true;
```

`VITE_DATA_MODE=mock`은 항상 로컬 모드, `shared`는 항상 서버 모드입니다. 생략하면 브라우저는 Mock으로 실행되고, 토스 WebView는 Supabase 설정이 있을 때 공유 방으로 실행됩니다. 브라우저 초대는 HTTPS 웹 링크를, 토스 공유 방은 SDK가 만든 `intoss://secret-five/r/…` 기반 링크를 사용합니다.

## 결제와 이용권 실험

- 결과에 추가로 열릴 카드가 있으면 단건(이번 방 열기)을 기본 선택으로 표시하고, 그 아래에 1,900원 전 팩 자유이용 패스를 함께 보여 줍니다. 패스는 구매한 현재 방과 이후 그 기기에서 만드는 네 팩의 방에 모두 적용됩니다. 두 좌석은 같은 결과를 보고, 기기 패스는 구매자에게만 귀속됩니다. 브라우저 데이터 삭제 시 기기 식별도 사라집니다.
- 통한 카드가 0장이거나 두 장 이하(잠글 카드 없음)면 구매 버튼을 숨깁니다. 받는 사람이 **이번엔 내가 새 5장 보내기**를 누르면 방금 답한 5장을 제외하고 바로 다음 판의 첫 질문을 보여줍니다. 다섯 답을 봉인하기 전에는 초대 링크가 생성되지 않습니다.
- 실제 매출은 실결제 연동 후 측정합니다. 지금은 테스트 DB에서만 완료 방 수, 완료된 답장 방 수, 두 상품의 모의 주문 수와 금액을 UTC 날짜·팩별로 집계합니다. 기본 브라우저 Mock은 집계 서버에 전송하지 않습니다.
- 아래 쿼리는 Supabase SQL Editor에서 운영자가 실행합니다. 최근 30일의 완료 방 100개당 모의 결제 금액과 답장으로 시작해 완료된 방 수를 보여줍니다. 답장 방 수는 고유 사용자 수와 다릅니다. 003 적용 후부터 기록되며, 시행 전후 수치 비교에는 동일한 관측 기간이 필요합니다.

```sql
select pack, sum(completed_rooms) as completed,
       sum(replay_completed_rooms) as completed_replies,
       sum(room_purchases) as single_orders, sum(pack_purchases) as pass_orders,
       round(100.0 * sum(room_krw + pack_krw) / nullif(sum(completed_rooms), 0)) as mock_krw_per_100
from secret_five_private.daily_metrics
where day >= (now() at time zone 'UTC')::date - 29
group by pack;
```

## 제품 결정

- **결제 모델(5.0)**. 방을 만들고 링크를 보내는 것은 모든 팩에서 무료입니다. 둘 다 YES인 카드는 **두 장까지 무료**로 열고, 나머지 '통한 카드'와 카드별 한마디는 그 방에서 한 번 **단건 결제**(**우리 썸인가**·**내가 그렇게 좋아?**·**질투 나는데** 1,100원, **썸 끝내기** 1,496원)하거나 **전 팩 자유이용 패스 1,900원**으로 엽니다. 패스는 이 기기에서 만드는 네 팩 결과를 모두 열고, 초대받은 사람도 같은 방의 열린 결과를 봅니다. 테마 화면에는 1번 팩에만 `2장 무료`를 표시하고 아래에 `보내기 무료 · 결과는 결제 · 패스 1,900원`을 적어 결제를 미리 알립니다. 누가 YES/NO를 골랐는지는 끝까지 공개하지 않고, 어긋난 카드는 `아쉽게 엇갈린 질문 N장`으로만 표시합니다.
- 질문 60개와 화면 문구는 [src/questions.json](src/questions.json) 한 곳에서만 관리합니다. 2026-11-21 3.0 개편에서 "어장인지, 연애로 갈 마음인지" 같은 취조조 질문을 걷어내고, 은근한 우선순위·거리 좁히기·작은 호감의 증거·둘만의 다음 장면을 묻는 60문항으로 다시 썼습니다. 결과 문구는 여운 한 줄과 바로 이어질 한 줄만 남겼습니다. 2026-11-22 4.0 개편은 "입 밖으로 꺼내면 들킬까 봐 못 묻는, 썸 타는 사이의 현실 속마음"으로 60문항을 전면 교체했습니다. 모든 문항은 둘 다 yes를 눌렀을 때 호감이 인정되는 방향으로만 쓰고, 카톡 구어체를 씁니다. 팩4는 노골적 19금·잠자리 유도 문항을 전부 걷어내고 늦은 밤 헤어지기 아쉬운 순간·고백 직전의 텐션·단둘일 때의 설렘만 담았습니다. 2026-11-27에는 4개 팩 제목을 **우리 썸인가 · 내가 그렇게 좋아? · 질투 나는데 · 썸 끝내기**로 확정하고 팩2 15문항을 인생네컷·이어폰·드라이브·우산 같은 장면 중심으로 다시 썼습니다(쉼표 없는 구어체 유지, `id`/`sku`/`price_krw` 그대로). 생성기는 `work/mj-questions-gen-v4.py`입니다.
- 첫 화면은 AI 일러스트·상황 칩·3단 가이드를 걷어내고, 웜 오프화이트 바탕·타이포그래피 카드 더미·간결한 팩 리스트·하나의 CTA만 남겼습니다. 팩 썸네일도 이미지 대신 번호와 제목으로 표시합니다.
- 기본 구성은 네 팩을 모두 표시합니다. `VITE_AUDIENCE=teens` 빌드는 팩4와 연결 칩을 숨기고 팩4 방 진입을 제한합니다(4.0에서 팩4가 노골적 표현을 쓰지 않게 되었지만 빌드 구분은 그대로 둡니다). 팩4의 **결과 이미지** 저장·공유는 제공하지 않습니다.
- 결제는 이번 MVP에서 모의 지급으로 동작합니다. 실결제 SDK 주문·영수증 검증·환불 복원은 출시 연동 항목입니다. 보상형 광고는 SDK 연동·모의 시청까지 붙였고, 콘솔 광고 그룹 ID와 서버 검증이 남았습니다.

## 보상형 광고

결과 화면에서 잠긴 통한 카드가 한 장 이상 남았을 때(세 장 이상 통했을 때), 결제 버튼 아래에 **광고 보고 1장 무료로 더 열기**가 붙습니다. 방마다 한 번만 쓸 수 있고, 광고를 끝까지 봐서 `userEarnedReward` 이벤트를 받은 경우에만 카드 한 장이 열립니다. 중간에 닫으면 보상이 없고 다시 볼 수 있습니다. 광고로 한 장을 연 뒤에도 남은 카드는 결제로 엽니다.

- 코드: `src/bridge.ts`의 `showRewardedAd`, `src/Results.tsx`의 광고 버튼, `src/domain.ts`의 `matchCards(..., adBonus)`.
- 광고 그룹 ID는 `VITE_TOSS_REWARDED_AD_GROUP_ID`로 넣습니다. 없으면 SDK 문서의 테스트 ID(`ait-ad-test-rewarded-id`)로 동작합니다. 테스트 ID는 광고가 나오지만 수익은 없으니, 출시 전에 앱인토스 콘솔에서 보상형 광고 그룹을 만들고 발급된 ID를 `.env.local`과 콘솔 빌드 환경에 넣습니다.
- 브라우저 미리보기에는 실제 광고가 없어 1.6초짜리 모의 시청으로 전체 흐름을 체험합니다. `?ad=skip`은 중간에 닫은 경우, `?ad=fail`은 광고를 못 불러온 경우를 흉내 냅니다.
- 공유 방은 `supabase/migrations/004_rewarded_ad.sql`의 `secret_five_ad`(ad_state/ad_reward)로 방 단위 보상을 기록합니다. 이 마이그레이션이 없는 서버에서는 광고 버튼을 숨기고 결제만 안내합니다(기존 001~003은 그대로 동작).
- 실제 출시에서는 광고 시청 완료를 토스 서버 검증으로 바꾸는 것이 원칙입니다. 지금은 앱이 광고를 본 뒤 호출하는 신뢰 방식입니다(모의 결제와 같은 단계).

## 직접 확인할 항목

- 앱인토스 콘솔에서 앱 이름이 `secret-five`인지 확인하고 테스트 번들을 올립니다. 콘솔의 연령 등급과 빌드 대상도 함께 확인합니다.
- 토스 iOS·Android에서 상하단 Safe Area, OS 뒤로가기, 카드 스와이프와 햅틱, 큰 글자와 동작 줄이기를 확인합니다. SDK 인셋 초기 조회와 구독을 사용하며 브라우저에서는 CSS safe-area로 대체합니다.
- 두 실제 기기에서 공유 방을 사용해 카카오톡 초대, 미니앱 복귀, 두 번째 제출 직후 양쪽 결과 갱신을 확인합니다.
- 모의 잠금 해제를 취소하거나 완료한 뒤 새로 고쳐 봅니다. 모든 팩에서 둘 다 YES인 카드는 두 장까지 열리고, 세 장 이상 통했을 때만 결제 버튼이 나오며 결제 전후로 열린 카드 수가 달라지는지 확인합니다(무료 팩도 같습니다).
- 공유 방에서 광고 버튼을 눌러 1장이 더 열리는지, 새로 고쳐도 버튼이 돌아오지 않는지, 반대 좌석에도 같은 카드가 보이는지 확인합니다.

## 공유 방 서버의 결제 규칙 (005 적용 완료)

`supabase/migrations/005_preview_two_and_pass.sql`이 서버를 5.0 규칙에 맞춥니다. 앱 코드는 그대로이고, 실서버(`VITE_SUPABASE_URL`)를 붙이려면 이 파일을 프로젝트에 한 번 실행하면 됩니다.

- `state`: 둘 다 YES인 카드는 **두 장까지**만 `opened`로 내려갑니다(무료 팩 포함). 세 장 이상이면 나머지는 `matched - 2`장이 잠긴 채 남고, 결제나 광고로 엽니다.
- `test_unlock`(이 방 열기): 무료 팩도 허용하고, 금액은 **1,100원**(썸 끝내기 1,496원)입니다. 잠글 카드가 없으면(겹친 카드 두 장 이하) `NO_LOCKED_MATCHES`로 막습니다.
- `test_pack_pass`(전 팩 자유이용 패스): pack2 전용·3,300원 규칙을 없애고 **어느 팩 방에서든 1,900원**으로 기록합니다. 패스는 `secret_five_private.all_passes`에 기기 단위로 남고, 이후 그 기기가 만드는 네 팩 방은 만들 때부터 열립니다. 패스를 이미 가진 기기가 다른 방을 열어도 주문은 다시 기록하지 않습니다.
- 003에서 판 **pack2 전용 3,300원 이용권**(`pack2_passes`)은 이미 산 기기에 한해 pack2에서만 계속 인정합니다.
- `secret_five_ad`: 광고로 여는 카드를 무료 두 장 다음(겹친 카드의 세 번째)으로 옮겼습니다. 무료 팩도 세 장 이상 통하면 광고로 한 장이 열립니다.

**같이 점검한 것**

- `state` 응답은 `pack`·`nick`·`created`·`ids`(결과 전에만)·`matched`·`unlocked`·`opened` 일곱 개 키뿐입니다. 상대의 원본 답(`host_answers`·`guest_answers`)과 어긋난 카드 id, 카드별 잠금 사유는 어떤 경우에도 내려가지 않으며, `opened`는 둘 다 YES인 카드만 담습니다. 겹친 개수(`matched`)는 결과 화면이 쓰는 값이라 내려갑니다.
- 방 코드는 8자 `[a-z0-9]`(36⁸ ≈ 2.8조, 약 41비트)로 추측으로 겹칠 일이 없고, 실제 잠금은 좌석 토큰(32바이트 · 43자)입니다. 코드만 알면 `state`도 결제도 `INVALID_LINK`로 거절됩니다.

**원격 DB 적용 전에 확인할 점**

- 저장소에는 `supabase/config.toml`이나 Supabase CLI 연결이 없고 `.env.local`(gitignore)에 프로젝트 URL·공개 키만 있습니다. 그래서 자동 `supabase db push`는 불가능하고, 대시보드 SQL Editor에서 005 파일 내용을 붙여 실행하거나 `supabase link` 후 `supabase db push`를 쓰면 됩니다.
- 005는 다시 실행해도 안전합니다(`create table if not exists` + `create or replace function`). 이 파일 하나로 `secret_five`와 `secret_five_ad` 두 함수가 함께 바뀌므로, 적용 직후 앱을 다시 열어 결과 화면의 열린 카드 수를 확인하세요.
- 모의 결제(`test_purchases`)는 제 DB에서 꺼야 합니다. 켜져 있으면 누구나 `test_unlock`·`test_pack_pass`를 무료로 부를 수 있습니다.

적용 후 아래 질의로 005가 들어갔는지 확인할 수 있습니다(둘 다 `true`여야 합니다).

select to_regclass('secret_five_private.all_passes') is not null as has_all_passes,
